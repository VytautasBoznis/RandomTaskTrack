# Core engine build — 2026-08-02

First build of the backend. Core engine only, no domain-specific features yet.

## Decisions worth remembering

**Materialize, don't compute.** Recurring tasks are written into `task_tasks`
ahead of time (21-day horizon, hourly `RecurrenceMaterializerHostedService`)
rather than derived on read. Two reasons: the dashboard stays a plain indexed
query, and a generated instance can be edited or annotated individually without
special-casing "this one isn't real yet".

Safety comes from the partial unique index `ux_task_tasks_recurrence_due`
(`recurrence_id, due_on`), which lets `TryCreateFromRecurrenceAsync` use
`ON CONFLICT DO NOTHING` — so the materializer is safe to run on a timer, on
demand after a create/update, and concurrently, with no locking.

**`anchor_mode` is the interesting bit of the schedule model.**
- `FromSchedule` (1) — fixed cadence, generated by the horizon sweep.
- `FromCompletion` (2) — the next instance is chained by `CompleteTaskOperation`,
  measured from the actual completion date. Only ever one open instance at a
  time; the sweep seeds the first one and then leaves it alone.

That is what makes "cleaned the bathroom on day 9 of a 7-day cycle → next is day
16, not day 14" work. It is the answer to the recurrence question that has no
universally right default.

**Timezone.** `IClock.Today` resolves in `Scheduler:TimeZone`, not UTC. Due
dates are calendar dates, so a UTC-derived "today" rolls over at the wrong local
hour. The runtime Docker image installs `tzdata` for this — without it every
IANA id silently falls back to UTC.

**Editing a recurrence's schedule** deletes *pending* instances from today
forward and rebuilds them. Completed history is never touched, which is also why
`task_tasks.recurrence_id` is `ON DELETE SET NULL` rather than `CASCADE`.

## A CHECK-constraint trap worth not repeating

The first cut of `ck_task_recurrences_shape` was written as
`array_length(days_of_week, 1) > 0` and `day_of_month BETWEEN 1 AND 31`. Both
silently let malformed rules through: `array_length('{}', 1)` is **NULL**, not
0, and a CHECK that evaluates to NULL counts as satisfied. Same for a NULL
`day_of_month`. Caught only by running the SQL against a real Postgres — the
constraint looked obviously correct on the page.

Every branch is now wrapped in `COALESCE(..., 0)`. **Any new CHECK involving a
nullable column needs the same treatment.**

## AI layer

`IAiProvider` is scoped to "one chat completion, with tools" — the level where
Anthropic, OpenAI and local models actually agree. Tool schemas are raw JSON
Schema strings so they pass through unchanged. Thinking/effort/caching are
**not** on the interface; they live in `AiOptions.ProviderOptions` and are read
only by the adapter that understands them.

The agent loop (`AiConversationService`) is hand-written rather than using the
SDK's `BetaToolRunner` — the runner is Anthropic-specific and would leak through
the abstraction, and owning the loop is what allows gating destructive tools and
persisting each turn as it happens. Bounded by `Ai:MaxToolIterations` (8).

Tool handlers run on the **caller's UnitOfWork**, so a chat turn is atomic.

## Known gaps

- `AiToolDefinition.RequiresConfirmation` is set on `delete_task` /
  `delete_recurrence` but nothing enforces it yet — the loop still auto-executes.
  Needs a pending-call round-trip through the API before the destructive tools
  are safe to leave unattended.
- No frontend.
- No first-user bootstrap: `/api/auth/register` is admin-gated, so the first
  user has to be inserted by hand (BCrypt hash, `role = 999`).
